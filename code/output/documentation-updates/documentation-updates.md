# Proposed Documentation Updates

These are recommendations only. The original documents were not modified.

## 1. Scope statement (suggested addition to Overview / College Report)

> This project is a local synthetic prototype. All workload, load, and latency
> values are generated by the simulator; no Azure resource is provisioned and no
> real telemetry is collected. A dashboard, REST API, SQLite history, FCFS, and an
> adaptive policy are included as clearly labeled extensions to the original
> requirements.

## 2. Policies (Modules / PRD)

Add a table distinguishing documented and extension policies:

| Policy | Type | Rule |
|---|---|---|
| Round-robin | Documented | Next healthy node |
| Least-loaded | Documented | Healthy node with lowest load; equal-load ties prefer fewer prior assignments |
| FCFS | Extension | First healthy node |
| Adaptive | Extension | Capacity-first when forecast exceeds headroom; otherwise least-loaded; equal-headroom ties prefer fewer prior assignments |

## 3. Surge detection (Modules / Test Plan)

State the exact rule:

> A rate surge is raised when the average of the last N interval request counts
> reaches the rate threshold. An average-load surge uses the mean load across all
> nodes. A maximum-load surge uses each interval's highest node load. Priority is
> rate, then maximum load, then average load; a cooldown suppresses repeats.

Add the implemented consequence:

> Maximum-node-load detection closes the previous FCFS blind spot. FCFS reaches
> 150% peak load and now records 9 surge events in a normal run, where the
> average-only rule recorded none. Thresholds remain heuristic and are not
> validated against labelled incidents.

## 4. Simulation model (Modules)

Document the constants:

- 3 nodes: 100, 100, 75 capacity.
- 10% seeded request variation.
- Load decay 0.55 per interval.
- 3.0 load points per normalized request (capped at 150%).
- Simulated latency `20 * (100/capacity) * (1 + load/100)` ms.
- Bounded admission control: requests wait above the overload threshold; full queues reject as overload; queued wait over the timeout fails. Queue wait is estimated per interval, not a discrete-event queue.

## 5. Forecast (Modules / Research)

Add:

- Forecast uses only prior intervals; the current interval is observed afterward.
- MAE/RMSE exclude the first interval (no history).
- `change_aware` is the default: it uses the latest observation when recent
  spread exceeds 20% of the mean, otherwise the moving average.
- Pure moving average (`ma_mae`/`ma_rmse`) and a causal last-value naive baseline
  (`naive_mae`/`naive_rmse`) are evaluated on the same intervals.
- Burst MAE is 18.56 for change-aware, 45.06 for pure MA, and 19.09 for naive
  (RMSE 45.73, 66.94, 46.89). Change-aware removes most of the MA lag but only
  marginally beats naive and cannot anticipate the first changed interval.
- On normal and failure traffic the selected/MA errors are 1.87/2.45 MAE versus
  2.46/3.23 for naive.

## 9. Experiment and results (Research / College Report)

Add the design and headline results:

- 4 scenarios x 4 policies x 5 seeds (7, 13, 29, 41, 53), 80 runs, 20 intervals,
  with t-based 95% confidence intervals. The overload scenario uses threshold 80,
  queue 10, and timeout 100 ms.
- Normal latency: FCFS 183.18 ms, round-robin 40.49 ms, least-loaded 37.02 ms,
  adaptive 37.02 ms. FCFS queued 80.3% of accepted requests.
- Burst latency: FCFS 211.02 ms, round-robin 190.94 ms, least-loaded 183.11 ms,
  adaptive 183.22 ms; all reached 150% peak load. FCFS accepted 58.8% versus
  93.5-96.8% for the others.
- Failure latency: FCFS 233.89 ms, round-robin 136.02 ms, least-loaded 137.15 ms,
  adaptive 136.29 ms; load-aware policies ended at 0.00 spread.
- Burst forecast MAE: change-aware 18.56, pure MA 45.06, naive 19.09; RMSE:
  45.73 / 66.94 / 46.89.
- Overload: FCFS/RR/LL/adaptive accepted 15.0/42.3/41.4/39.2% and completed
  71.9/66.1/69.9/80.0% of accepted requests. Timeouts were 28.1/33.9/30.1/20.0%.
- Accounting identities hold in all 80 runs: generated = accepted + rejected and
  accepted = completed + failed.
- State explicitly that five seeds and confidence intervals show repeatability,
  not formal significance.

## 11. Speaker notes corrections

Add or confirm these answers:

- "Does this autoscale Azure?" - No. Recommendations are advisory text only.
- "Is this real monitoring?" - No. Node load and latency are synthetic.
- "Did you deploy to Azure?" - No.
- "Which policy performed best?" - Least-loaded in this synthetic setup for
  balance and normal traffic; adaptive showed no meaningful gain after fair
  tie-breaking; not established by a significance test.
- "What was the detection weakness?" - The average-load rule missed a single hot
  node under FCFS. Maximum-node-load detection was added and FCFS now alerts;
  threshold precision/recall remains unmeasured.
- "Did you implement admission control?" - Yes, as a simplified extension:
  bounded per-node queues, overload rejection, and simulated timeouts. It is not
  a production queueing model.
- "Is the service secure?" - It has safe localhost defaults, optional bearer
  auth, body/volume caps, and opt-in CORS. It is not an internet-facing or
  multi-user security system.
